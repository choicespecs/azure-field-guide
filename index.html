Before chapter 1

New to cloud? Start here

Six ideas that make the rest of this guide click, plus a reading order for a developer or infrastructure role.

Cloud is renting, by the minute

Instead of buying servers, you ask Azure for a database or a web host and it appears in minutes. You pay while it exists, so deleting what you no longer need matters as much as creating it.

Everything is a resource

A VM, a database, a network, even a firewall rule set is a "resource" with a name, a region, a price tier (SKU) and settings. Resources live in resource groups, like folders.

Everything is an API call

Clicking "Create" in the portal sends the same request the CLI or a Bicep file sends. That is why teams describe infrastructure in code: it is just the list of requests, saved and repeatable.

Identity replaces passwords

Apps prove who they are with identities from Entra ID (managed identities), not passwords stored in config. When something says "access denied", the first question is: which identity, which role, at which scope?

Managed means less to patch

The higher up the stack you go (VM → App Service → Functions), the more Azure handles for you and the less control you have. Most new apps start at the PaaS layer.

Public by default, private by design

Many services start with a public endpoint on the internet. Production setups usually lock them into a private network. Much of an infrastructure job is that wiring.

Five habits that save beginners: put every experiment in its own resource group and delete the whole group when done · set a budget alert on any subscription you use · never paste keys or connection strings into code or chat · run what-if before every deployment · tag resources with owner and env.

Chapter 1

The mental model

Almost every Azure question gets easier once you know three things: where a resource sits in the hierarchy, which API you are talking to, and where it physically runs.

The scope hierarchy

Permissions (RBAC), policies, budgets and tags are assigned at a scope and inherit downward. Learn this ladder first.

scope 0Entra tenant

Your organization's identity directory (formerly Azure AD). Holds users, groups, app registrations. One tenant can own many subscriptions.Think: "who are you?"

scope 1Management groups

Folders for subscriptions, up to 6 levels deep under the tenant root group. Assign org-wide policy and RBAC here (e.g. "Corp", "Online", "Sandbox").Think: governance at scale

scope 2Subscriptions

The billing and quota boundary. Each has its own limits and invoice line. Teams commonly get one subscription per app per environment.Think: "who pays, and what are the limits?"

scope 3Resource groups

A lifecycle container. Resources that are deployed, updated and deleted together live in one group. A group has a region for its metadata, but its resources can live anywhere.Think: "what gets deleted together?"

scope 4Resources

The actual things: a VM, a storage account, a SQL database. Each has a resource ID like /subscriptions/{id}/resourceGroups/{rg}/providers/Microsoft.Storage/storageAccounts/{name}.Think: the unit you pay for

Control plane vs data plane

Every create, update or delete goes through Azure Resource Manager (ARM) at management.azure.com, whether you use the portal, CLI, Bicep or Terraform. That is the control plane.

Reading a blob or querying a database hits the service's own endpoint, e.g. myacct.blob.core.windows.net. That is the data plane, and it often has separate permissions.

Common trap: "Owner" on a storage account lets you manage it but does not grant reading blobs through Entra auth. You need a data role such as Storage Blob Data Reader.

Regions, zones, pairs

  • Region: a set of datacenters in a geography (e.g. eastus2, westeurope). Not every service or VM size exists in every region.
  • Availability zone: physically separate datacenters inside a region with independent power and cooling. Zone-redundant deployment survives one datacenter failing.
  • Region pair: two regions in the same geography used for sequenced platform updates and geo-replication (e.g. East US 2 ↔ Central US). Some newer regions have no pair.
  • Sovereign clouds: Azure Government and Azure operated by 21Vianet (China) are separate clouds with separate endpoints.

Resource providers

Services are exposed by namespaces like Microsoft.Compute, Microsoft.Web, Microsoft.Network. A subscription must have a provider registered before you can create its resources.

Each resource type has versioned APIs (2023-05-01 style). Bicep and ARM templates pin those versions, which is why templates keep working when the service changes.

az provider register -n Microsoft.App

Chapter 2

Identity & governance

Identity is the real perimeter in Azure. Most incidents and most "access denied" tickets come down to who can do what, at which scope.

Who: security principals

  • User: a person in Entra ID (or a guest via B2B).
  • Group: assign roles to groups, not individuals.
  • Service principal: an app's identity in a tenant, created from an app registration. Authenticates with a secret, certificate or federated credential.
  • Managed identity: a service principal Azure manages for you, with no secrets to rotate. System-assigned lives and dies with one resource; user-assigned is a standalone resource you can attach to many.
  • Workload identity federation: lets GitHub Actions, Kubernetes or another cloud get Entra tokens via OIDC with no stored secret.

What: Azure RBAC

A role assignment = principal + role definition + scope.

  • Owner: everything, including granting access.
  • Contributor: manage everything, but cannot grant access.
  • Reader: view only.
  • User Access Administrator / Role Based Access Control Administrator: manage role assignments only.
  • Hundreds of service-specific roles (e.g. Key Vault Secrets User, AcrPull).

Deny assignments exist but are created by the platform (e.g. Deployment Stacks, managed apps), not by you directly.

Entra roles ≠ Azure roles

Entra roles (Global Administrator, Application Administrator, User Administrator) control the directory: users, apps, licenses.

Azure RBAC roles control resources in subscriptions.

A Global Admin has no Azure resource access by default, though they can elevate themselves to User Access Administrator at root scope.

Hardening access

  • Conditional Access: rules like "require MFA and a compliant device to reach the Azure portal".
  • Privileged Identity Management (PIM): make admin roles eligible, then activate just-in-time with approval and a time limit.
  • Access reviews: periodic recertification of group and role membership.
  • Break-glass accounts: two cloud-only emergency admins excluded from most CA policies, closely monitored.

Azure Policy

Rules evaluated against resource properties. Assign a single definition or a bundle (initiative) at any scope.

Effects: Deny, Audit, Modify, Append, DeployIfNotExists, AuditIfNotExists, DenyAction, Disabled.

Typical uses: allowed regions, required tags, no public IPs, enforce diagnostic settings, enforce private endpoints.

Other guardrails

  • Tags: key/value metadata (env, owner, costCenter). Not inherited unless a policy copies them.
  • Resource locks: CanNotDelete or ReadOnly, applied even to Owners.
  • Cost Management + budgets: alerts at thresholds; cost analysis by tag, resource group or service.
  • Deployment Stacks: manage a set of resources as one unit, with deny settings to block out-of-band changes. The successor to Azure Blueprints.
  • Azure Landing Zones: Microsoft's reference management-group and policy layout from the Cloud Adoption Framework.

Chapter 5

How it fits together

Four shapes cover most of what you will see at work. Read each flow top to bottom and name every service in it. If you can, you understand the platform.

Pattern A

Secure web app with a database

flowchart LR
  U[Users] --> FD[Front Door + WAF]
  FD -->|Private Link| APP[App Service / Container Apps]
  APP -->|Managed identity| KV[Key Vault]
  APP -->|Private endpoint| SQL[(Azure SQL)]
  APP -->|Private endpoint| ST[(Blob Storage)]
  APP -.telemetry.-> AI[Application Insights]
  AI --> LA[Log Analytics]
  1. DNS points at Front Door, which terminates TLS at the edge, applies WAF rules and caches static content.
  2. Front Door reaches the app privately. The app has public access disabled.
  3. The app's managed identity fetches secrets from Key Vault and authenticates to SQL and Storage with Entra tokens, so there are no connection-string passwords.
  4. Outbound calls go through VNet integration to private endpoints; Private DNS zones resolve the service names to private IPs.
  5. Application Insights collects requests, dependencies and exceptions into a Log Analytics workspace.
Pattern B

Hub-and-spoke network (landing zone)

flowchart TB
  OP[On-premises] ---|ExpressRoute / VPN| GW
  subgraph HUB[Hub VNet - connectivity subscription]
    GW[VPN / ER Gateway]
    FW[Azure Firewall]
    BAS[Bastion]
    DNS[DNS Private Resolver]
  end
  subgraph S1[Spoke: App A prod]
    A1[App subnet]
    D1[Data subnet]
  end
  subgraph S2[Spoke: App B prod]
    A2[AKS subnet]
  end
  HUB <-->|peering| S1
  HUB <-->|peering| S2
  A1 -.UDR 0.0.0.0/0.-> FW
  A2 -.UDR 0.0.0.0/0.-> FW
  1. A central hub VNet holds shared services: gateways to on-prem, Azure Firewall, Bastion for admin access, and DNS.
  2. Each workload gets its own spoke VNet, usually in its own subscription, peered to the hub.
  3. User-defined routes send spoke traffic through the firewall, so spoke-to-spoke and internet egress is inspected centrally.
  4. NSGs filter traffic at the subnet or NIC level; the firewall does centralized L3–L7 filtering.
  5. Virtual WAN is the managed alternative when you have many regions or branches.
Pattern C

Event-driven processing

flowchart LR
  UP[Client upload] --> BLOB[(Blob Storage)]
  BLOB -->|BlobCreated| EG[Event Grid]
  EG --> FN[Function: validate]
  FN -->|command| SB[Service Bus queue]
  SB --> W[Container Apps job: process]
  W --> COS[(Cosmos DB)]
  COS -->|change feed| FN2[Function: notify]
  SB -.failures.-> DLQ[Dead-letter queue]
  1. A file lands in Blob Storage; Storage publishes a BlobCreated event to Event Grid.
  2. A Function validates it and drops a durable command on a Service Bus queue.
  3. A worker (Container Apps job, scaled by KEDA on queue length) does the heavy lifting and writes to Cosmos DB.
  4. The Cosmos change feed triggers downstream reactions. Failed messages go to the dead-letter queue for inspection.
Pattern D

Data and AI platform

flowchart LR
  SRC[Apps, SaaS, on-prem DBs] --> ADF[Data Factory / Fabric pipelines]
  IOT[Devices, logs] --> EH[Event Hubs]
  ADF --> LAKE[(OneLake / ADLS Gen2)]
  EH --> LAKE
  LAKE --> SPARK[Databricks / Fabric Spark]
  SPARK --> WH[Warehouse / Lakehouse]
  WH --> PBI[Power BI]
  LAKE --> SRCH[AI Search index]
  SRCH --> FOUNDRY[Foundry: models + agents]
  FOUNDRY --> APP2[Chat / copilot app]
  PUR[Purview] -.catalog + lineage.-> LAKE
  1. Batch sources come in through Data Factory or Fabric pipelines; streams come in through Event Hubs.
  2. Everything lands in a data lake (ADLS Gen2 or Fabric's OneLake) in open Delta/Parquet formats, usually in bronze/silver/gold layers.
  3. Spark (Databricks or Fabric) cleans and models the data; Power BI reports on it.
  4. For generative AI, documents are chunked and embedded into AI Search; an app in Microsoft Foundry retrieves from it and calls a model (retrieval-augmented generation).
  5. Purview catalogs data, tracks lineage and applies sensitivity labels.

param env string
param appPrincipalId string

Developer trackChapter 7

Building apps on Azure

What changes when your code runs in Azure: how it authenticates, where config lives, how you run things locally, how it ships, and how it stays observable. Examples are in Python; every pattern has a direct equivalent in .NET, JavaScript and Java.

1. How your code talks to Azure services

Use the official Azure SDK packages (azure-* in Python, Azure.* in .NET, @azure/* in JavaScript). Authenticate with DefaultAzureCredential. On your laptop it uses your az login session; in Azure it uses the app's managed identity. The same code works in both places, with no keys anywhere.

Storage + Key Vault with no secrets
# pip install azure-identity azure-storage-blob azure-keyvault-secrets
from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient
from azure.keyvault.secrets import SecretClient

# az login locally, managed identity in Azure
cred = DefaultAzureCredential()

blobs = BlobServiceClient(
    "https://stdemodev.blob.core.windows.net", credential=cred)
uploads = blobs.get_container_client("uploads")
uploads.upload_blob("hello.txt", b"hi", overwrite=True)

secrets = SecretClient(
    "https://kv-demo-dev.vault.azure.net", credential=cred)
api_key = secrets.get_secret("ThirdPartyApiKey").value
Service Bus send + receive
# pip install azure-servicebus azure-identity
from azure.identity import DefaultAzureCredential
from azure.servicebus import ServiceBusClient, ServiceBusMessage

ns = "sb-demo-dev.servicebus.windows.net"
with ServiceBusClient(ns, DefaultAzureCredential()) as sb:
    with sb.get_queue_sender("orders") as sender:
        sender.send_messages(ServiceBusMessage('{"orderId": 123}'))

    with sb.get_queue_receiver("orders", max_wait_time=5) as rx:
        for msg in rx:
            print(str(msg))
            rx.complete_message(msg)  # or abandon / dead-letter
The #1 first-week error: AuthorizationPermissionMismatch or 403 while using DefaultAzureCredential. Your identity can sign in but has no data-plane role. Ask for (or assign) the right one, e.g. Storage Blob Data Contributor, Key Vault Secrets User, Azure Service Bus Data Sender. Role assignments can take a few minutes to apply.

3. Configuration and secrets

App settings are environment variables

In App Service, Functions and Container Apps, the settings you configure show up in your code as environment variables, e.g. os.environ["QUEUE_NAME"]. Keep non-secret config here.

Key Vault references

Point an app setting at a secret and the platform fetches it with the app's managed identity:

@Microsoft.KeyVault(VaultName=kv-demo;SecretName=DbPassword)

Your code still just reads an env var.

App Configuration

For config shared across many services, or feature flags you want to flip without redeploying. It can hold Key Vault references too.

Best of all: no secret at all

Azure SQL, Storage, Service Bus, Cosmos DB, Event Hubs, Key Vault and Azure OpenAI all accept Entra tokens. If a service supports managed identity, use it and skip the connection-string password.

5. Making code cloud-ready

Expect transient failures

  • Networks blip and services throttle (HTTP 429, 503). Azure SDKs retry with backoff by default; don't wrap them in a second retry loop.
  • Set timeouts on every outbound call.
  • Make message handlers idempotent: the same message may arrive twice.

Be stateless

  • Instances get added, removed and restarted. Keep sessions in Redis or a database, files in Blob Storage, never on local disk.
  • Expose a /health endpoint and wire it to the platform's health check or probes.

Instrument from day one

Add the Azure Monitor OpenTelemetry distro and you get requests, dependencies, exceptions and logs in Application Insights:

from azure.monitor.opentelemetry import configure_azure_monitor
configure_azure_monitor()

It reads APPLICATIONINSIGHTS_CONNECTION_STRING from the environment.

Signing in your users

  • Workforce apps: register the app in Entra ID and use MSAL, or turn on App Service's built-in auth ("Easy Auth") with no code.
  • Customer-facing apps: Entra External ID.
  • APIs validate the token's audience and scopes; API Management can do this at the gateway.

Developer gotchas

Works locally, 403 in Azure

Locally you used your own identity; in Azure the app's managed identity is used, and it lacks the role. Assign the role to the managed identity.

App can't reach the database after networking was locked down

Public access was disabled. The app needs VNet integration plus a private endpoint, and DNS must resolve to the private IP.

Settings changes restart the app

Changing App Service app settings restarts it. Use slots or App Configuration for live changes.

Functions run slowly at first

Cold start on consumption plans. Use Flex Consumption's always-ready instances or a Premium plan for latency-sensitive endpoints.

Cosmos DB bill is surprisingly high

Usually cross-partition queries or a hot partition key. Check RU charge per query in the response headers.

Time zones are wrong

Azure services run in UTC. Store and compare times in UTC; convert only for display.

Infrastructure trackChapter 8

Running the platform

The infrastructure side: planning networks, structuring IaC, promoting through environments, troubleshooting connectivity and keeping costs and patches under control.

What the work usually is

  • Provisioning subscriptions, networks and shared services from code
  • Reviewing pull requests to IaC repos and pipelines
  • Granting and auditing access (RBAC, PIM requests)
  • "Why can't X reach Y?" network tickets
  • Patching, backups, DR tests
  • Cost reviews and cleanup
  • Responding to alerts and Defender for Cloud findings

Environments and promotion

  • Separate subscriptions (or at least resource groups) for dev, test and prod, so a mistake in dev can't touch prod and costs stay visible.
  • The same IaC deploys every environment; only parameter files differ.
  • Pipelines promote dev → test → prod with what-if output and an approval gate before prod.
  • Nobody clicks changes into prod by hand. If they must in an emergency, fix the code afterward so the next deploy doesn't undo it (drift).

3. Troubleshooting "X can't reach Y"

  1. DNS. Does the name resolve, and to the right IP? For a private endpoint you should get a 10.x address, not a public one. Most private-networking problems are DNS problems.
  2. Port reachable? Test TCP from the source: nc -vz host 1433 or Test-NetConnection host -Port 1433.
  3. NSGs. Check effective security rules on the source and destination NICs or subnets.
  4. Routes. Check effective routes; a UDR may send traffic to a firewall that drops it.
  5. Firewall. Search Azure Firewall logs for the source IP.
  6. Service firewall. The PaaS resource's own "Networking" settings may block public access or not list your subnet.
  7. Identity. If you connect but get 401/403, it's RBAC, not networking.
Commands for each step
# 1 DNS: expect a private 10.x IP for private endpoints
nslookup stdemoprod.blob.core.windows.net

# 2 TCP reachability from the source machine
nc -vz sql-demo-prod.database.windows.net 1433

# 3 effective NSG rules on a VM's NIC
az network nic list-effective-nsg -g rg-app-prod -n nic-vm01

# 4 effective routes on that NIC
az network nic show-effective-route-table \
  -g rg-app-prod -n nic-vm01 -o table

# Network Watcher end-to-end check
az network watcher test-connectivity -g rg-app-prod \
  --source-resource vm01 \
  --dest-address sql-demo-prod.database.windows.net --dest-port 1433

Chapter 9

Monitoring & operations

Azure Monitor is the umbrella. Underneath it, nearly everything ends up as rows in a Log Analytics workspace that you query with KQL.

The telemetry pipeline

  • Platform metrics: numeric time series every resource emits for free (CPU, requests, DTU). 93-day retention.
  • Activity log: who did what at the control plane: "user X deleted VM Y". Subscription-level.
  • Resource logs: data-plane detail (e.g. Key Vault access, firewall hits). Off by default; turn on with diagnostic settings.
  • Azure Monitor Agent + Data Collection Rules: collect VM guest OS logs and perf counters.
  • Application Insights: APM for your code, with OpenTelemetry support.

Acting on it

  • Alerts: metric, log-search, activity-log and service-health rules.
  • Action groups: who to notify and what to trigger (email, SMS, webhook, Logic App, ITSM).
  • Workbooks and Azure Managed Grafana: dashboards.
  • Service Health: Azure's own incidents and planned maintenance affecting your resources.
  • Advisor: recommendations on cost, security, reliability and performance.

Keeping things running

  • Azure Backup: VMs, SQL in VMs, Files, Blobs, AKS, into Recovery Services or Backup vaults.
  • Site Recovery: replicate VMs to another region and fail over.
  • Update Manager: OS patching for Azure and Arc-enabled machines.
  • Network Watcher: connection troubleshoot, IP flow verify, flow logs.
  • Resource Health: is this resource healthy right now?
KQL you will use weekly
// Failed requests by operation, last 24h (Application Insights)
AppRequests
| where TimeGenerated > ago(24h) and Success == false
| summarize failures = count() by OperationName, ResultCode
| order by failures desc

// Who deleted or changed things (Activity log)
AzureActivity
| where TimeGenerated > ago(7d)
| where OperationNameValue endswith "DELETE" or OperationNameValue endswith "WRITE"
| project TimeGenerated, Caller, OperationNameValue, ResourceGroup, _ResourceId
| order by TimeGenerated desc

// p95 latency in 5-minute buckets
AppRequests
| where TimeGenerated > ago(6h)
| summarize p95 = percentile(DurationMs, 95) by bin(TimeGenerated, 5m)
| render timechart

// Resource Graph: every storage account that still allows public blob access
resources
| where type == "microsoft.storage/storageaccounts"
| where properties.allowBlobPublicAccess == true
| project name, resourceGroup, subscriptionId, location
Chapter 10

The Well-Architected Framework

Microsoft's design-review vocabulary. Expect architects to use these five pillars by name, and expect trade-offs between them.

PillarThe questionTypical Azure answers
ReliabilityDoes it survive failure and recover on time?Availability zones, multi-region with Front Door, geo-replication, Backup, health probes, retries with backoff, defined RTO/RPO
SecurityIs access minimal and is data protected?Entra ID + managed identities, private endpoints, Key Vault, Defender for Cloud, WAF, encryption with customer-managed keys where required
Cost OptimizationAre we paying only for value?Right-sizing, autoscale, reservations and savings plans, spot VMs, storage tiering, budgets, tagging for showback
Operational ExcellenceCan we deploy and run it safely?IaC, CI/CD with approvals, monitoring and alerts, runbooks, safe deployment (slots, canary), blameless postmortems
Performance EfficiencyDoes it scale with demand?Autoscale rules, caching (Redis, Front Door), partitioning, async messaging, load testing with Azure Load Testing

The Cloud Adoption Framework (CAF) is the companion for the organization side: strategy, plan, ready (landing zones), adopt (migrate/innovate), govern, secure and manage. The Well-Architected Framework is per-workload; CAF is per-organization.
