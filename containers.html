Containers & Kubernetes

Containers show up in almost every Azure team, whether apps run on Container Apps, App Service or AKS. This chapter covers the vocabulary, the build-and-push loop, and enough Kubernetes to read your team's manifests.

The vocabulary

TermWhat it meansWhere it lives in Azure
ImageA packaged app plus everything it needs to run, built from a DockerfileStored in Azure Container Registry (ACR)
RegistryA store of images, addressed as registry/repo:tagmyacr.azurecr.io/orders-api:1.4.2
ContainerA running instance of an imageContainer Apps replica, App Service instance, AKS pod
PodKubernetes' smallest unit: one or more containers sharing a network addressAKS
DeploymentKeeps N copies of a pod running and rolls out new versionsAKS (Container Apps does this for you with revisions)
ServiceA stable internal address that load-balances across podsAKS; type: LoadBalancer creates an Azure Load Balancer
Ingress / GatewayHTTP routing from outside the cluster to servicesApp Routing add-on (NGINX), Application Gateway for Containers
NamespaceA folder inside a cluster for separating teams or appsAKS
ConfigMap / SecretConfig and sensitive values injected into podsPrefer Key Vault via the Secrets Store CSI driver
Node poolThe VMs that run pods; system pools run cluster services, user pools run your appsVM Scale Sets managed by AKS
Helm chartA templated, versioned package of Kubernetes manifestsOften stored in ACR as OCI artifacts
Workload identityLets a pod use a managed identity to call Azure services with no secretsAKS with OIDC issuer enabled
Dockerfile for a small Flask API
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# run as a non-root user
RUN useradd -m appuser
USER appuser

EXPOSE 8000
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]
Build in the cloud, push to ACR
# create a registry (name must be globally unique, letters/digits)
az acr create -g rg-demo-dev -n acrdemodev$RANDOM --sku Basic

# build remotely with ACR Tasks: no Docker needed locally
az acr build -r <acrName> -t orders-api:1.0.0 .

# list what's in the registry
az acr repository list -n <acrName> -o table
az acr repository show-tags -n <acrName> --repository orders-api

# or build locally and push
az acr login -n <acrName>
docker build -t <acrName>.azurecr.io/orders-api:1.0.0 .
docker push <acrName>.azurecr.io/orders-api:1.0.0

Reading a Kubernetes manifest

deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  namespace: orders
spec:
  replicas: 3                     # keep 3 pods running
  selector:
    matchLabels: { app: orders-api }
  template:
    metadata:
      labels:
        app: orders-api
        azure.workload.identity/use: "true"
    spec:
      serviceAccountName: orders-api   # linked to a managed identity
      containers:
        - name: api
          image: acrdemodev.azurecr.io/orders-api:1.0.0
          ports: [{ containerPort: 8000 }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 256Mi }
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
---
apiVersion: v1
kind: Service
metadata:
  name: orders-api
  namespace: orders
spec:
  selector: { app: orders-api }
  ports: [{ port: 80, targetPort: 8000 }]
AKS + kubectl essentials
# small lab cluster that can pull from your registry
az aks create -g rg-demo-dev -n aks-demo \
  --node-count 1 --node-vm-size Standard_B2s \
  --attach-acr <acrName> \
  --enable-oidc-issuer --enable-workload-identity \
  --generate-ssh-keys

# point kubectl at it
az aks install-cli               # if kubectl isn't installed
az aks get-credentials -g rg-demo-dev -n aks-demo

# apply and inspect
kubectl create namespace orders
kubectl apply -f deployment.yaml
kubectl get pods -n orders -o wide
kubectl describe pod <pod> -n orders    # events explain most failures
kubectl logs deploy/orders-api -n orders --tail=50
kubectl port-forward svc/orders-api 8080:80 -n orders

# roll out a new version and watch it
kubectl set image deploy/orders-api api=<acr>.azurecr.io/orders-api:1.0.1 -n orders
kubectl rollout status deploy/orders-api -n orders
kubectl rollout undo deploy/orders-api -n orders

# stop paying for the lab
az aks stop -g rg-demo-dev -n aks-demo

Pod troubleshooting cheat sheet

ImagePullBackOff

Wrong image name or tag, or the cluster can't authenticate to ACR. Check the tag exists and run az aks check-acr -g <rg> -n <aks> --acr <acr>.azurecr.io.

CrashLoopBackOff

The container starts then exits. Read kubectl logs <pod> --previous; usually a missing env var or a bad startup command.

Pending

No node has room. kubectl describe pod shows "Insufficient cpu/memory". Lower requests or scale the node pool.

OOMKilled

The container used more memory than its limit. Raise the limit or fix the leak.

Running but not receiving traffic

The readiness probe is failing, or the Service's selector doesn't match the pod labels. Check kubectl get endpoints.

403 calling Azure from a pod

Workload identity isn't wired up: the service account annotation, the federated credential on the managed identity, or the role assignment is missing.

Same app, less platform: everything above maps onto Container Apps without managing a cluster. A Deployment becomes a container app, a rollout becomes a revision, and HPA/KEDA scaling becomes a scale rule. The Kubernetes terms still matter, because Container Apps' docs and error messages use them.
