Running the platform

The infrastructure side: planning networks, structuring IaC, promoting through environments, troubleshooting connectivity and keeping costs and patches under control.

What the work usually is

  • Provisioning subscriptions, networks and shared services from code
  • Reviewing pull requests to IaC repos and pipelines
  • Granting and auditing access (RBAC, PIM requests)
  • "Why can't X reach Y?" network tickets
  • Patching, backups, DR tests
  • Cost reviews and cleanup
  • Responding to alerts and Defender for Cloud findings

Environments and promotion

  • Separate subscriptions (or at least resource groups) for dev, test and prod, so a mistake in dev can't touch prod and costs stay visible.
  • The same IaC deploys every environment; only parameter files differ.
  • Pipelines promote dev → test → prod with what-if output and an approval gate before prod.
  • Nobody clicks changes into prod by hand. If they must in an emergency, fix the code afterward so the next deploy doesn't undo it (drift).

1. IP address planning

Address ranges are painful to change later and must never overlap with on-premises networks or other VNets you might peer with. A small example plan:

VNet / subnetRangeUsable IPsNotes
vnet-hub-prod10.0.0.0/221,019Shared connectivity services
· GatewaySubnet10.0.0.0/2727Name is required exactly; VPN/ExpressRoute gateways
· AzureFirewallSubnet10.0.0.64/2659Required name and minimum /26
· AzureBastionSubnet10.0.0.128/2659Required name and minimum /26
vnet-app-prod10.1.0.0/221,019One workload spoke
· snet-app10.1.0.0/2659Delegated to App Service for VNet integration
· snet-pe10.1.0.64/2659Private endpoints for SQL, Storage, Key Vault
vnet-aks-prod10.2.0.0/204,091Kubernetes needs room to grow; overlay networking keeps pod IPs out of the VNet

Azure reserves 5 addresses in every subnet (the first four and the last), so a /27 gives 27 usable, not 32. Leave gaps between ranges for growth.

2. Structuring infrastructure code

Bicep: project layout + module wiring
infra/
  main.bicep              // composes the modules
  main.dev.bicepparam     // per-environment values
  main.prod.bicepparam
  modules/
    network.bicep
    app.bicep
    data.bicep
    monitoring.bicep

// main.prod.bicepparam
using './main.bicep'
param env = 'prod'
param location = 'eastus2'
param appSkuName = 'P1v3'

// main.bicep
param env string
param location string
param appSkuName string

module net 'modules/network.bicep' = {
  name: 'network'
  params: {
    env: env
    location: location
    addressPrefix: '10.1.0.0/22'
  }
}

module app 'modules/app.bicep' = {
  name: 'app'
  params: {
    env: env
    location: location
    skuName: appSkuName
    subnetId: net.outputs.appSubnetId  // outputs flow between modules
  }
}

# terraform init → plan → apply
Bicep or Terraform? Use whatever your team already uses. The concepts (modules, parameters, outputs, plan/what-if, environments) carry over directly. Bicep keeps no state file and gets new Azure features first. Terraform covers other clouds and SaaS, but you have to manage its state.

3. Troubleshooting "X can't reach Y"

  1. DNS. Does the name resolve, and to the right IP? For a private endpoint you should get a 10.x address, not a public one. Most private-networking problems are DNS problems.
  2. Port reachable? Test TCP from the source: nc -vz host 1433 or Test-NetConnection host -Port 1433.
  3. NSGs. Check effective security rules on the source and destination NICs or subnets.
  4. Routes. Check effective routes; a UDR may send traffic to a firewall that drops it.
  5. Firewall. Search Azure Firewall logs for the source IP.
  6. Service firewall. The PaaS resource's own "Networking" settings may block public access or not list your subnet.
  7. Identity. If you connect but get 401/403, it's RBAC, not networking.
Commands for each step
# 1 DNS: expect a private 10.x IP for private endpoints
nslookup stdemoprod.blob.core.windows.net

# 2 TCP reachability from the source machine
nc -vz sql-demo-prod.database.windows.net 1433

# 3 effective NSG rules on a VM's NIC
az network nic list-effective-nsg -g rg-app-prod -n nic-vm01

# 4 effective routes on that NIC
az network nic show-effective-route-table \
  -g rg-app-prod -n nic-vm01 -o table

# Network Watcher end-to-end check
az network watcher test-connectivity -g rg-app-prod \
  --source-resource vm01 \
  --dest-address sql-demo-prod.database.windows.net --dest-port 1433

4. Cost and hygiene

Pay less for the same thing

  • Reservations (1 or 3 years) for steady VMs, SQL and Cosmos DB
  • Savings plans for compute that changes shape
  • Spot VMs for interruptible batch work
  • Azure Hybrid Benefit if you own Windows Server or SQL licenses
  • Auto-shutdown and scale-to-zero for dev environments
Resource Graph: find waste
// unattached managed disks (still billed)
resources
| where type == "microsoft.compute/disks"
| where properties.diskState == "Unattached"
| project name, resourceGroup, sku.name, properties.diskSizeGB

// public IPs not attached to anything
resources
| where type == "microsoft.network/publicipaddresses"
| where isnull(properties.ipConfiguration)
    and isnull(properties.natGateway)
| project name, resourceGroup, location

// resources missing an owner tag
resources
| where isnull(tags.owner)
| summarize count() by type
