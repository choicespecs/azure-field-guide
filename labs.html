Chapter 12

Walkthroughs

Five end-to-end examples of common setups. Each one creates its own resource group so you can delete everything with one command at the end. Run them in a bash shell (macOS Terminal, WSL or Cloud Shell) after az login.

Before you start: use a personal or sandbox subscription, not your employer's production one. Each walkthrough lists rough cost; most cost cents if you delete them the same day. Set LOC to a region near you that your subscription allows.

1 · Web app that reads a Key Vault secret with managed identity

~45 min · B1 plan

Deploys a Flask app to App Service with a managed identity that reads a secret from Key Vault through an app setting, with no password anywhere.

Step 1: create the resources
RG=rg-lab1; LOC=eastus2; SFX=$RANDOM
APP=app-lab1-$SFX; KV=kv-lab1-$SFX

az group create -n $RG -l $LOC
az appservice plan create -n plan-lab1 -g $RG --sku B1 --is-linux
az webapp create -n $APP -g $RG -p plan-lab1 --runtime "PYTHON:3.12"

# turn on a system-assigned managed identity
az webapp identity assign -n $APP -g $RG
APP_PRINCIPAL=$(az webapp identity show -n $APP -g $RG --query principalId -o tsv)

# Key Vault using Azure RBAC for permissions
az keyvault create -n $KV -g $RG -l $LOC --enable-rbac-authorization true
KV_ID=$(az keyvault show -n $KV --query id -o tsv)
ME=$(az ad signed-in-user show --query id -o tsv)

# you can write secrets; the app can only read them
az role assignment create --assignee $ME --role "Key Vault Secrets Officer" --scope $KV_ID
az role assignment create --assignee-object-id $APP_PRINCIPAL \
  --assignee-principal-type ServicePrincipal \
  --role "Key Vault Secrets User" --scope $KV_ID

# role assignments take a minute or two to apply
sleep 60
az keyvault secret set --vault-name $KV -n Greeting --value "hello from Key Vault"

# app setting that points at the secret
az webapp config appsettings set -n $APP -g $RG \
  --settings "GREETING=@Microsoft.KeyVault(VaultName=$KV;SecretName=Greeting)"
Step 2: write and deploy the app
mkdir lab1 && cd lab1
printf 'flask\ngunicorn\n' > requirements.txt
cat > app.py <<'PY'
import os
from flask import Flask
app = Flask(__name__)

@app.get("/")
def index():
    return os.environ.get("GREETING", "GREETING is not set")
PY

az webapp up -n $APP -g $RG --runtime "PYTHON:3.12"
curl https://$APP.azurewebsites.net

Verify: the page prints "hello from Key Vault". In the portal, open the app → Settings → Environment variables; the GREETING row shows a green Key Vault reference status. If it shows an error, the role assignment hadn't applied yet: restart the app after a minute.

What failure looks like: if the identity loses its role, the app receives the raw @Microsoft.KeyVault(...) text instead of the secret value.

Clean up
az group delete -n $RG --yes --no-wait
# Key Vault soft-deletes; purge it so the name can be reused
az keyvault purge -n $KV

2 · Lock a storage account behind a private endpoint

~40 min · B1s VM

Builds a VNet and puts a storage account behind a private endpoint with public access off. DNS resolves to a private IP from inside the VNet but not from your laptop.

Build it
RG=rg-lab2; LOC=eastus2; ST=stlab2$RANDOM
ZONE=privatelink.blob.core.windows.net

az group create -n $RG -l $LOC
az network vnet create -g $RG -n vnet-lab2 --address-prefix 10.10.0.0/16 \
  --subnet-name snet-vm --subnet-prefixes 10.10.1.0/24
az network vnet subnet create -g $RG --vnet-name vnet-lab2 \
  -n snet-pe --address-prefixes 10.10.2.0/24

# storage with no public network access
az storage account create -n $ST -g $RG -l $LOC --sku Standard_LRS \
  --public-network-access Disabled --allow-blob-public-access false
ST_ID=$(az storage account show -n $ST -g $RG --query id -o tsv)

# private endpoint for the blob service
az network private-endpoint create -g $RG -n pe-$ST \
  --vnet-name vnet-lab2 --subnet snet-pe \
  --private-connection-resource-id $ST_ID --group-id blob --connection-name blob-conn

# private DNS so the normal name resolves to the private IP
az network private-dns zone create -g $RG -n $ZONE
az network private-dns link vnet create -g $RG -n link-lab2 -z $ZONE -v vnet-lab2 -e false
az network private-endpoint dns-zone-group create -g $RG --endpoint-name pe-$ST \
  -n default --private-dns-zone $ZONE --zone-name blob

# a VM with no public IP to test from
az vm create -g $RG -n vm-lab2 --image Ubuntu2204 --size Standard_B1s \
  --vnet-name vnet-lab2 --subnet snet-vm --public-ip-address "" \
  --admin-username azureuser --generate-ssh-keys
Prove it
# from your laptop: public answer, and requests are refused
nslookup $ST.blob.core.windows.net

# from inside the VNet: a 10.10.2.x address
az vm run-command invoke -g $RG -n vm-lab2 --command-id RunShellScript \
  --scripts "nslookup $ST.blob.core.windows.net"

Verify: inside the VNet the name resolves through {name}.privatelink.blob.core.windows.net to a 10.10.2.x address. Without the DNS zone link, the VM resolves the public IP and the connection fails. That's the most common private-endpoint bug.

Clean up
az group delete -n $RG --yes --no-wait

3 · Container Apps that scale to zero

~30 min · pay per use

Runs a public container on Container Apps with an HTTP scale rule: replicas appear under load and drop to zero when idle.

Deploy and scale
az extension add --name containerapp --upgrade
az provider register -n Microsoft.App --wait
az provider register -n Microsoft.OperationalInsights --wait

RG=rg-lab3; LOC=eastus2
az group create -n $RG -l $LOC

# creates the environment, Log Analytics workspace and app in one go
az containerapp up -n ca-lab3 -g $RG -l $LOC \
  --image mcr.microsoft.com/k8se/quickstart:latest \
  --target-port 80 --ingress external

# scale between 0 and 5 replicas, 10 concurrent requests each
az containerapp update -n ca-lab3 -g $RG \
  --min-replicas 0 --max-replicas 5 \
  --scale-rule-name http-rule --scale-rule-type http \
  --scale-rule-http-concurrency 10

URL=https://$(az containerapp show -n ca-lab3 -g $RG \
  --query properties.configuration.ingress.fqdn -o tsv)
echo $URL
Generate load and watch
# terminal 1: send ~500 requests in parallel batches
for i in $(seq 1 10); do
  for j in $(seq 1 50); do curl -s -o /dev/null $URL & done; wait
done

# terminal 2: watch replicas
watch -n 5 "az containerapp replica list -n ca-lab3 -g $RG -o table"

# revisions: each config change makes a new one
az containerapp revision list -n ca-lab3 -g $RG -o table

Verify: replicas climb above 1 under load, then drop to 0 a few minutes after the load stops. The next request after that is slower; that's a cold start. Then find the app's logs in its Log Analytics workspace with ContainerAppConsoleLogs_CL | take 20.

Clean up
az group delete -n $RG --yes --no-wait

4 · Deploy Bicep from GitHub Actions with no secrets

~45 min · storage only

Creates an Entra app that trusts a GitHub repo through OIDC, grants it Contributor on one resource group, and deploys a Bicep file on every push to main.

Step 1: identity and trust (run once)
REPO=your-github-user/your-repo     # change this
RG=rg-lab4; LOC=eastus2

az group create -n $RG -l $LOC
APP_ID=$(az ad app create --display-name gh-lab4-deployer --query appId -o tsv)
az ad sp create --id $APP_ID

# least privilege: Contributor on this one resource group only
az role assignment create --assignee $APP_ID --role Contributor \
  --scope $(az group show -n $RG --query id -o tsv)

# trust tokens from pushes to main in your repo
az ad app federated-credential create --id $APP_ID --parameters "{
  \"name\": \"gh-main\",
  \"issuer\": \"https://token.actions.githubusercontent.com\",
  \"subject\": \"repo:$REPO:ref:refs/heads/main\",
  \"audiences\": [\"api://AzureADTokenExchange\"]
}"

# store the IDs as repo variables (they are not secrets)
gh variable set AZURE_CLIENT_ID -R $REPO -b $APP_ID
gh variable set AZURE_TENANT_ID -R $REPO -b $(az account show --query tenantId -o tsv)
gh variable set AZURE_SUBSCRIPTION_ID -R $REPO -b $(az account show --query id -o tsv)
infra/main.bicep
param location string = resourceGroup().location

resource st 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: 'stlab4${uniqueString(resourceGroup().id)}'
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
  properties: {
    allowBlobPublicAccess: false
    minimumTlsVersion: 'TLS1_2'
  }
  tags: { lab: '4', deployedBy: 'github-actions' }
}

output name string = st.name
.github/workflows/deploy.yml
name: deploy-infra
on:
  push:
    branches: [main]
permissions:
  id-token: write
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - run: az deployment group what-if -g rg-lab4 -f infra/main.bicep
      - run: az deployment group create -g rg-lab4 -f infra/main.bicep

Verify: push to main, open the Actions tab, and confirm the what-if step lists the storage account as "Create". Run it again and what-if shows "NoChange". Bicep deployments are idempotent.

Gotcha: the federated credential's subject must match exactly how the job runs. If you add environment: prod to the job, the subject becomes repo:OWNER/REPO:environment:prod and you need a second credential. The error is AADSTS700213: No matching federated identity record found.

Clean up
az group delete -n rg-lab4 --yes --no-wait
az ad app delete --id $APP_ID

5 · KQL against the free demo workspace

~30 min · free

Microsoft hosts a demo Log Analytics workspace full of sample telemetry. Open it from the Log Analytics tutorial to try these query patterns.

Five KQL patterns
// 1 look at a table: always start small
AppRequests | take 10

// 2 filter rows and pick columns
AppRequests
| where TimeGenerated > ago(1h) and Success == false
| project TimeGenerated, Name, ResultCode, DurationMs

// 3 aggregate
AppRequests
| where TimeGenerated > ago(1d)
| summarize requests = count(), avgMs = avg(DurationMs) by Name
| top 10 by requests

// 4 time series and a chart
AppRequests
| where TimeGenerated > ago(1d)
| summarize count() by bin(TimeGenerated, 15m), Success
| render timechart

// 5 join requests to the exceptions they caused
AppRequests
| where TimeGenerated > ago(1d) and Success == false
| join kind=inner (AppExceptions | project OperationId, ExceptionType, OuterMessage) on OperationId
| summarize count() by Name, ExceptionType
| order by count_ desc

Note: each | passes the previous result to the next operator. Query 4's shape (filter, bin by time, count) is the same one a log alert rule uses.
