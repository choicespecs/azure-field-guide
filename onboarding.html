Mapping an environment

Every Azure estate is set up differently. The questions to answer about any environment you work in, and read-only commands that answer some of them directly.

Access

  • Which Entra tenant(s) and subscriptions will I work in?
  • How do I request access, and is it through PIM (just-in-time)?
  • Is there a sandbox subscription where I can experiment?
  • Which Entra groups should I be in?
  • Do I need a separate admin account for privileged work?

How things ship

  • Where is the infrastructure code: Bicep, Terraform, or both?
  • Azure DevOps or GitHub? Where do pipelines live?
  • What environments exist, and how does a change reach prod?
  • Who approves production changes? Is there change management?
  • Are there internal modules or templates I should reuse?

The platform

  • Is there a landing zone? Who owns the hub network?
  • What naming and tagging conventions do we use?
  • Which Azure Policies will block me (regions, SKUs, public IPs)?
  • Which services are approved, and which are off-limits?
  • Where do logs go, and which dashboards does on-call use?
  • Who owns cost, and are there budgets per team?
Inventory an environment (read-only)
# which tenants and subscriptions can I see?
az account list --query "[].{name:name, id:id, tenant:tenantId, default:isDefault}" -o table

# what access do I actually have?
az role assignment list --assignee $(az ad signed-in-user show --query id -o tsv) --all \
  --query "[].{role:roleDefinitionName, scope:scope}" -o table

# management group tree (if you can read it)
az account management-group list -o table

# what's deployed, by type, across everything I can see
az graph query -q "resources | summarize count() by type | order by count_ desc" --first 50 -o table

# which resource groups exist and how are they tagged?
az group list --query "[].{name:name, location:location, tags:tags}" -o table

# which policies apply to this subscription?
az policy assignment list --query "[].{name:displayName, scope:scope}" -o table

Working habits

  • Keep a personal notes file of resource names, subscription IDs and who owns what.
  • Keep an up-to-date architecture diagram of each production app you touch.
  • Read the last few incident write-ups; they show where the system really breaks.
  • Read an app's IaC before changing anything in the portal.

Things to avoid

  • Creating resources in a production subscription to "try something".
  • Changing anything in the portal that is managed by IaC; the next deploy will revert it, or worse.
  • Regenerating storage or Cosmos DB keys: every app using the old key breaks.
  • Deleting resource groups you didn't create, even if they look abandoned.
  • Pasting connection strings, keys or tokens into chat, tickets or AI tools.
